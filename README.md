# 天依わな育成シミュレーション 開発指示書

## 1. プロジェクト概要

HTML・CSS・JavaScriptを使用して、天依わなを中心とする育成シミュレーションゲームを開発する。

ゲームはノベルゲーム形式の会話画面と、時間・スタミナ・好感度などを管理するシミュレーション要素を組み合わせる。

開発は1人で行うため、保守性・可読性・拡張性を重視する。

## 2. 最重要ルール

以下を必ず守ること。

1. 既存プロジェクトの構造を確認してから実装する。
2. 既存のHome・Loading・Config画面を無断で作り直さない。
3. 既存コードを変更する場合は、必要最小限にとどめる。
4. HTML・CSS・JavaScriptは原則として分離する。
5. シナリオをJavaScript内に直接大量記述しない。
6. シナリオはYAMLで管理し、実行時に直接読み込む。
7. イベントやエンディングを追加しても、ゲーム本体の変更が最小限で済むようにする。
8. 未確定事項を勝手に確定仕様として扱わない。
9. 仕様が不足している場合は、実装前に質問する。
10. 将来のFirebase連携を考慮するが、初期段階ではFirebaseを必須にしない。

## 3. 開発環境

- Vite
- JavaScript（ES Modules）
- HTML
- CSS
- YAML
- IndexedDB

React・VueなどのUIフレームワークは使用しない。

既存プロジェクトの依存関係を確認し、不要なライブラリは追加しない。

## 4. ゲーム進行

2025年4月から2026年3月までの52ステージで構成する。

1ステージは約1週間に相当する。

各ステージの日時や名称はYAMLで管理する。

ゲーム内部の時間は分単位で管理し、画面には時間帯と時刻を表示する。

固定の行動回数制限は設けない。

ステージ終了時刻に到達したら確認モーダルを表示し、次のステージへ進める。

時間超過は次ステージの開始時刻に影響する。

## 5. パラメータ

以下を管理する。

- 好感度：0～100
- スタミナ：通常最大100、内部的なマイナス値を許可
- 登録者数：0以上の整数
- ストーリーフラグ
- イベント履歴
- 現在ステージ
- 現在時刻
- 難易度

スタミナが0未満の場合、画面には0と表示する。

スタミナ不足でも行動できるが、不足量と難易度に応じて好感度ペナルティを発生させる。

消費量・回復量・補正値は設定データから変更できるようにする。

## 6. 難易度

以下の2種類を実装する。

- 甘口
- 辛口

難易度はゲーム開始時に選択し、プレイ途中では変更できない。

難易度によって、スタミナ消費量・好感度変化量・イベント条件・限定イベント・エンディング条件を変更できる構造にする。

具体的な補正値は調整可能な設定として管理する。

## 7. 行動システム

行動をカテゴリ別に管理する。

想定する行動は以下のとおり。

- 会話
- 移動
- 食事
- 休憩
- 勉強・練習
- 配信準備
- 配信
- 特殊イベント

行動の実行前に時間コストとスタミナコストを表示する。

食事・休憩の回復量は固定値とする。

## 8. イベントシステム

イベントはYAMLで定義し、一意のイベントIDを付与する。

発生条件にはAND・ORを使用できるようにする。

イベントごとに以下を設定できる構造とする。

- 発生条件
- 優先度
- 発生確率
- 一度きり・繰り返し・クールダウン
- 会話内容
- 選択肢
- パラメータ変更
- フラグ変更
- 分岐先イベントID
- 関連エンディング
- 後回し時の再提示条件

複数イベントが発生可能な場合は、基本優先度と未回収エンドへの関連性を考慮する。

イベントの後回し機能を実装し、再提示時には発生条件を再確認する。

イベントの会話再生自体では原則として時間を進めない。

## 9. エンディング

初期実装では以下の2種類を用意する。

- 途中離脱
- 完走

途中離脱はイベントによって即時発生・ステージ終了時判定を使い分ける。

エンディングの判定は、重要な選択肢・イベント履歴・パラメータ・難易度などに対応する。

エンディングは後から追加可能なデータ構造にする。

回収済みエンディングは全セーブスロット共通で管理する。

エンディング一覧・回収率・回想再生・攻略ヒント表示に対応する。

## 10. セーブシステム

初期実装ではIndexedDBを使用する。

- 手動セーブ：5枠
- 自動セーブ：1枠
- 手動セーブは安全なタイミングのみ
- 自動セーブは行動終了時とステージ切り替え時
- JSONエクスポート対応
- JSONインポート非対応

将来的なFirebase連携に備えて、保存処理をゲーム本体から分離する。

## 11. UI

ゲーム画面はノベルゲーム形式を基本とする。

背景とキャラクター立ち絵を中心に表示し、下部に会話ウィンドウを配置する。

簡易ステータスを常時表示し、詳細情報は別画面で確認できるようにする。

マウス・タッチ・キーボード操作に対応する。

会話ログ・オート再生・既読スキップ・キーボードショートカットに対応する。

PC向けの横長画面を基本とし、スマートフォンでも操作できるようにする。

既存のHome・Loading・Config画面は、実際のコードを確認してから必要な機能を接続する。

## 12. デバッグ・検証

以下を実装する。

- 現在のパラメータ確認
- ストーリーフラグ確認
- 発生可能イベントの確認
- 任意ステージからのテスト開始
- テスト用セーブデータ生成
- YAMLの構文・参照整合性検証

YAML検証は開発用コマンドとゲーム起動時の両方で実行する。

致命的なエラーは実行停止、軽微な問題は警告とする。

## 13. 将来実装する機能

初期基盤完成後、以下を追加する。

- Firebase Authentication
- Cloud Firestore
- アカウント登録・ログイン
- クラウドセーブ
- ゲストデータの引き継ぎ
- オフラインプレイ
- 自動同期・手動同期
- 複数端末の競合解決

Firebaseの認証情報や管理者権限をクライアントコードに埋め込まないこと。

Firestore Security Rulesによって、各ユーザーが自分の保存データだけを読み書きできるようにすること。

## 14. 実装の進め方

最初に既存ファイルを調査し、現在の実装状況を報告する。

その後、実装順序と変更対象ファイルを提示する。

承認された範囲から段階的に実装する。

最初の目標は、ゲストプレイで52ステージを進行でき、セーブ・ロード・エンディング回収まで動作する最小構成を完成させることである。

シナリオ本文や数値バランスが未確定の場合は、明確にテストデータと分かる仮データを使用する。

本番シナリオとして勝手に確定しないこと。

まずはコードを変更せず、既存プロジェクトの調査と実装計画の提示から開始すること。
