# 天依わな育成シミュレーション 開発指示書

## 1. プロジェクト概要

HTML・CSS・JavaScriptを使用して、天依わなを中心とする育成シミュレーションゲームを開発する。

ゲームはノベルゲーム形式の会話画面と、時間・スタミナ・好感度などを管理するシミュレーション要素を組み合わせる。

開発は1人で行うため、保守性・可読性・拡張性を重視する。

## 2. 最重要ルール

以下を必ず守ること。

1. 既存プロジェクトの構造を確認してから実装する。
2. 既存のHome・Loading・Config画面を無断で作り直さない。
3. 既存コードを変更する場合は、必要最小限にとどめる。
4. HTML・CSS・JavaScriptは原則として分離する。
5. シナリオをJavaScript内に直接大量記述しない。
6. シナリオはYAMLで管理し、実行時に直接読み込む。
7. イベントやエンディングを追加しても、ゲーム本体の変更が最小限で済むようにする。
8. 未確定事項を勝手に確定仕様として扱わない。
9. 仕様が不足している場合は、実装前に質問する。
10. Firebase AuthenticationとCloud Firestoreを使い、セーブデータをクラウド管理する。

## 3. 開発環境

- Vite
- JavaScript（ES Modules）
- HTML
- CSS
- YAML
- Firebase Authentication
- Cloud Firestore

React・VueなどのUIフレームワークは使用しない。

既存プロジェクトの依存関係を確認し、不要なライブラリは追加しない。

### ローカルで起動する（Windows PowerShell）

事前にFirebase Web設定が `.env.local` に入力されていることを確認し、VS Codeのターミナルで次を貼り付けてください。

```powershell
Set-Location C:\GitHub\Honey-Trap-byHTML
npm install
npm run dev
```

ターミナルに表示されたURL（通常は `http://localhost:5173/`）をブラウザーで開きます。終了するときはターミナルで `Ctrl+C` を押してください。

`.env.local` がまだない場合だけ、次を一度実行してからFirebase Webアプリの設定値を入力してください。既存の `.env.local` は上書きしないでください。

```powershell
Copy-Item .env.example .env.local
```

必須設定が空のままではゲームを起動できません。Firebase Authenticationの匿名認証とCloud Firestoreも有効にしてください。

### Cloudflare Pagesで公開する

Cloudflare PagesのGit連携設定は次のとおりです。

- Build command: `npm run build`
- Build output directory: `dist`
- Root directory: リポジトリのルート（通常は空欄）

`dist` はViteが生成する本番用ファイルです。リポジトリのルートをそのまま静的ファイルとして公開すると、未ビルドの `/src/main.js` が読み込まれ、CSSやYAMLをJavaScriptモジュールとして扱うエラーになります。設定を保存したら再デプロイしてください。

Direct Uploadを使う場合は、ローカルで `npm run build` を実行し、生成された `dist` フォルダーの中身をアップロードしてください。リポジトリのソース一式はアップロードしないでください。

Firebase設定値はCloudflare Pagesの環境変数にも登録してください。Viteはビルド時に `VITE_` で始まる環境変数を取り込むため、ProductionとPreviewそれぞれ必要な環境へ登録した後に再ビルド・再デプロイします。デプロイ後のページソースで `/src/main.js` ではなく `/assets/` 配下のJavaScriptとCSSが参照されていることを確認してください。

## 4. ゲーム進行

2025年4月から2026年3月までの52ステージで構成する。

1ステージは約1週間に相当する。

各ステージの日時や名称はYAMLで管理する。

ゲーム内部の時間は分単位で管理し、画面には時間帯と時刻を表示する。

固定の行動回数制限は設けない。

ステージ終了時刻に到達したら確認モーダルを表示し、次のステージへ進める。

時間超過は次ステージの開始時刻に影響する。

## 5. パラメータ

以下を管理する。

- 好感度：0～100
- スタミナ：通常最大100、内部的なマイナス値を許可
- 登録者数：0以上の整数
- ストーリーフラグ
- イベント履歴
- 現在ステージ
- 現在時刻
- 難易度

スタミナが0未満の場合、画面には0と表示する。

スタミナ不足でも行動できるが、不足量と難易度に応じて好感度ペナルティを発生させる。

消費量・回復量・補正値は設定データから変更できるようにする。

## 6. 難易度

以下の2種類を実装する。

- 甘口
- 辛口

難易度はゲーム開始時に選択し、プレイ途中では変更できない。

難易度によって、スタミナ消費量・好感度変化量・イベント条件・限定イベント・エンディング条件を変更できる構造にする。

具体的な補正値は調整可能な設定として管理する。

## 7. 行動システム

行動をカテゴリ別に管理する。

想定する行動は以下のとおり。

- 会話
- 移動
- 食事
- 休憩
- 勉強・練習
- 配信準備
- 配信
- 特殊イベント

行動の実行前に時間コストとスタミナコストを表示する。

食事・休憩の回復量は固定値とする。

## 8. イベントシステム

イベントはYAMLで定義し、一意のイベントIDを付与する。

発生条件にはAND・ORを使用できるようにする。

イベントごとに以下を設定できる構造とする。

- 発生条件
- 優先度
- 発生確率
- 一度きり・繰り返し・クールダウン
- 会話内容
- 選択肢
- パラメータ変更
- フラグ変更
- 分岐先イベントID
- 関連エンディング
- 後回し時の再提示条件

複数イベントが発生可能な場合は、基本優先度と未回収エンドへの関連性を考慮する。

イベントの後回し機能を実装し、再提示時には発生条件を再確認する。

イベントの会話再生自体では原則として時間を進めない。

## 9. エンディング

初期実装では以下の2種類を用意する。

- 途中離脱
- 完走

途中離脱はイベントによって即時発生・ステージ終了時判定を使い分ける。

エンディングの判定は、重要な選択肢・イベント履歴・パラメータ・難易度などに対応する。

エンディングは後から追加可能なデータ構造にする。

回収済みエンディングは全セーブスロット共通で管理する。

エンディング一覧・回収率・回想再生・攻略ヒント表示に対応する。

## 10. セーブシステム

Firebase AuthenticationとCloud Firestoreを使用する。

- 手動セーブ：5枠
- 自動セーブ：1枠
- 手動セーブは安全なタイミングのみ
- 自動セーブは行動終了時とステージ切り替え時
- JSONエクスポート対応
- エクスポート済みJSONをクラウドへインポート可能

保存処理はゲーム本体から分離し、クラウド接続に失敗した場合はローカルへ自動で切り替えずエラーを表示する。

## 11. UI

ゲーム画面は背景と文章を主役にしたサウンドノベル形式とし、人物の立ち絵を常時表示しない。人物が必要な場面のみ、シナリオから指定したローカル画像またはCSS仮シルエットを背景へ重ねる。

素材は `public/images/backgrounds/` と `public/images/silhouettes/` に配置し、YAMLでは `/images/backgrounds/...` または `/images/silhouettes/...` のURLパスで指定する。各フォルダのREADMEに記述例があります。

話者名と地の文を区別した下部テキストウィンドウを設け、クリック・タップ・Enter・Spaceで文章を送る。オート再生、既読スキップ、バックログを利用できる。ステージ表示の下にスタミナ・好感度の小型グラフと数値、登録者数を表示し、詳細なステータスはメニューから確認できる。

操作はマウス・タッチ・キーボードに対応し、PCとスマートフォンの画面幅に合わせてレイアウトする。セーブ・ロード・設定・タイトルへの移動は本編メニューから行う。

行動は本編画面内の選択パネルから実行する。行動の説明、時間・スタミナコスト、実行後のパラメータ変化をホバーまたはキーボードフォーカスで確認でき、数値はゲームエンジンのプレビューを利用する。画面側でゲーム数値や難易度計算を重複実装しない。

既存のHome・Loading・Config画面は、実際のコードを確認してから必要な機能を接続する。

## 12. デバッグ・検証

以下を実装する。

- 現在のパラメータ確認
- ストーリーフラグ確認
- 発生可能イベントの確認
- 任意ステージからのテスト開始
- テスト用セーブデータ生成
- YAMLの構文・参照整合性検証

YAML検証は開発用コマンドとゲーム起動時の両方で実行する。

致命的なエラーは実行停止、軽微な問題は警告とする。

## 13. Firebaseクラウドセーブ

- 匿名認証で開始し、後からGoogleアカウントを連携する。
- 手動5枠・オート1枠とエンディング回収記録をFirestoreへ保存する。
- オフライン時にローカルへ自動フォールバックしない。保存・ロード失敗を画面に表示する。
- 既存のエクスポート済みJSONはロード画面から選択してクラウドへ取り込める。
- Firebase Web設定値は `.env.local` で管理する。Web APIキーはブラウザーから見える公開設定値であり、Firebase Security Rulesと承認済みドメイン制限を必ず設定する。サービスアカウントキー等の秘密情報はクライアントへ含めない。
- Firestore Security Rulesにより、各ユーザーは自分のUID配下のデータだけを読み書きできる。
- Webhook通知はCloud Functionsから送る。通知本文にメールアドレス、UID、パスワード、認証トークンを含めない。Webhook URLはFunctions Secretに保存する。

Firebase Consoleで匿名認証・Googleプロバイダー・Cloud Firestoreを有効化し、`.env.example` を `.env.local` にコピーしてFirebase Webアプリ設定値を入力する。ローカル保存への自動フォールバックは行わない。

## 14. 実装の進め方

最初に既存ファイルを調査し、現在の実装状況を報告する。

その後、実装順序と変更対象ファイルを提示する。

承認された範囲から段階的に実装する。

最初の目標は、ゲストプレイで52ステージを進行でき、セーブ・ロード・エンディング回収まで動作する最小構成を完成させることである。

シナリオ本文や数値バランスが未確定の場合は、明確にテストデータと分かる仮データを使用する。

本番シナリオとして勝手に確定しないこと。

まずはコードを変更せず、既存プロジェクトの調査と実装計画の提示から開始すること。
# 🎨 デザインシステム・配色ルール（天依わなゲームプロジェクト）

このプロジェクトのUIコンポーネント、HTML、CSSを記述・修正する際は、以下の配色ルールとデザインコンセプトを厳守してください。

## 1. デザインコンセプト
- **世界観**: 「天使だけど小悪魔系でメスガキ、かわいい」ギャップと中毒性のあるトーン。
- **ベーストーン**: 清楚な白銀・透明感をベースにしつつ、あざといピンクと危険な可愛さを演出するアクセントカラーを配置する。

## 2. CSS変数（定義済みカラーパレット）
必ず以下のCSS変数を使用し、ハードコード（直接の色指定）は避けてください。

```css
:root {
  --bg-main: #FAFAFC;        /* 画面全体のベース背景（清楚な白） */
  --window-bg: #FFF0F5;      /* テキストウィンドウやパネルの背景（ミルキーパステルピンク） */
  --text-color: #2D1B2D;     /* 通常テキスト・メインUI枠（深みのある紫紺） */
  --accent-pink: #FF3366;    /* メインアクセント・ボタン・選択肢・小悪魔ピンク */
  --accent-ruby: #D61C4E;    /* ホバー時・重要ハイライト・ルビーレッド */
}
```

## 3. 色の使い分け

| 用途 | 使用する色 | 適用例 |
|---|---|---|
| 画面全体・余白 | `var(--bg-main)` | ページ背景、画面のベース |
| 会話・情報パネル | `var(--window-bg)` | 会話ウィンドウ、カード、モーダル |
| 文字・基本の境界線 | `var(--text-color)` | 本文、見出し、アイコン、枠線 |
| 主操作・選択中 | `var(--accent-pink)` | 主ボタン、選択肢、選択中の項目 |
| hover・重要な強調 | `var(--accent-ruby)` | ボタンのhover、重要な警告、現在位置の強調 |

## 4. 実装ルール

- UIの色はCSS変数を通して指定する。コンポーネント内に色コードを直接書かず、必要な色が増える場合は `:root` に用途が分かる変数を追加する。
- 通常時・hover時・選択時・無効時・フォーカス時の状態を区別する。状態は色だけに頼らず、ラベル、枠線、形状なども併用する。
- 読みやすさを優先し、本文色には `--text-color`、本文背景には `--bg-main` または `--window-bg` を使用する。アクセント色を長文の本文色として使わない。
- `--accent-pink` と `--accent-ruby` は主に操作や短い強調に使い、広い面積を塗りつぶす用途では使いすぎない。
- ボタンやリンクのキーボードフォーカスを視認できるようにし、操作可能な要素の状態を色以外でも判別できるようにする。
- 新しい画面やコンポーネントを作る際は、このパレットと既存の画面構成を確認してから適用する。既存画面全体の配色を変更する場合は、関連画面で一貫性を確認する。

```css
.page {
  color: var(--text-color);
  background: var(--bg-main);
}

.dialogue-window {
  color: var(--text-color);
  background: var(--window-bg);
}

.button--primary {
  color: var(--text-color);
  background: var(--accent-pink);
}

.button--primary:hover {
  background: var(--accent-ruby);
}
```
